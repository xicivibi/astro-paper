CSV를 더블클릭했는데 한글이 `���`처럼 보이거나 모든 값이 한 열에 몰렸다면, 바로 저장하지 않는 편이 안전합니다. 깨진 상태로 다시 저장하면 원래 바이트나 열 구조를 복구하기 어려워질 수 있기 때문입니다.

문제는 보통 다음 세 층 중 하나에 있습니다.

1. **인코딩**: 같은 바이트를 UTF-8, CP949 같은 서로 다른 문자표로 읽었습니다.
2. **구분자**: 파일은 세미콜론이나 탭을 썼는데 프로그램이 콤마로 해석했습니다.
3. **CSV 구조**: 값 안의 콤마·줄바꿈·큰따옴표가 올바르게 감싸지지 않았습니다.

아래 순서대로 확인하면 원인을 섞지 않고 진단할 수 있습니다.

## 1. 원본을 복사하고 자동 변환을 멈춥니다

먼저 원본을 복사해 별도 파일에서 작업합니다. Excel은 CSV를 열 때 현재 기본 데이터 형식 설정으로 각 열을 해석할 수 있습니다. 날짜, 긴 숫자, 앞자리 0이 있는 코드가 의도와 다르게 바뀔 수 있으므로, 중요한 파일은 더블클릭보다 **데이터 → 텍스트/CSV에서** 가져오는 방법이 안전합니다.

Microsoft의 [텍스트·CSV 가져오기 안내](https://support.microsoft.com/en-us/excel/get-started/import-or-export-text-txt-or-csv-files)는 가져오기 화면에서 구분자를 선택하고 미리보기로 결과를 확인하는 절차를 설명합니다.

## 2. BOM은 단서이지 인코딩 전체의 증명은 아닙니다

UTF-8 BOM은 파일 맨 앞에 붙는 `EF BB BF` 세 바이트입니다. Microsoft는 UTF-8 CSV에 BOM이 있으면 Excel에서 정상적으로 열 수 있다고 안내합니다. BOM이 없는 UTF-8 파일은 **데이터 → 데이터 가져오기 → 텍스트/CSV에서** 경로로 가져오는 방법을 제시합니다.

다만 다음 두 판단을 구분해야 합니다.

- **BOM 있음**: UTF-8로 작성됐다는 강한 단서입니다.
- **BOM 없음**: UTF-8이 아니라는 뜻은 아닙니다.

이 사이트의 [CSV 파일 점검 도구](/tools/csv-preview/)는 BOM 유무만 표시하고 인코딩을 확정하지 않습니다. 브라우저의 `TextDecoder`가 잘못된 UTF-8 바이트를 대체 문자 `�`로 바꾼 경우에는 경고를 표시합니다. MDN도 기본적인 비엄격 디코딩에서 잘못된 바이트가 `U+FFFD`로 대체된다고 설명합니다.

## 3. 한 열에 몰리면 구분자를 먼저 봅니다

CSV라는 이름과 달리 현실의 표 형식 파일은 콤마 외에도 탭, 세미콜론, 파이프를 구분자로 사용합니다. Excel의 공식 안내도 탭 구분 텍스트와 콤마 구분 CSV를 나눠 설명하며, 가져오기 화면에서 구분자를 변경할 수 있다고 명시합니다.

간단한 예시는 다음과 같습니다.

```text
name;city;note
Kim;Seoul;"alpha,beta"
Lee;Busan;plain
```

이 파일을 콤마로 나누면 첫 행이 세 열로 보이지 않습니다. 반면 세미콜론을 선택하면 `name`, `city`, `note`가 분리됩니다. 값 안의 `alpha,beta`는 큰따옴표 안에 있으므로 열을 나누는 구분자로 취급하면 안 됩니다.

[CSV 파일 점검 도구](/tools/csv-preview/)는 앞부분의 여러 레코드에서 콤마·탭·세미콜론·파이프가 얼마나 일관되게 열을 만드는지 비교합니다. 결과는 “가능성 높은 구분자”이며 확정 판정이 아닙니다. 실제 가져오기 전에 헤더와 몇 개의 데이터 행이 같은 열 수로 보이는지 확인하세요.

## 4. 값 안의 콤마와 줄바꿈은 큰따옴표로 감쌉니다

[RFC 4180](https://www.rfc-editor.org/info/rfc4180/)은 널리 쓰이는 CSV 형식을 정리한 정보성 문서입니다. 핵심 규칙은 다음과 같습니다.

- 각 레코드는 줄바꿈으로 나눕니다.
- 한 레코드의 필드 수는 일관되게 유지하는 편이 좋습니다.
- 필드 안에 콤마, 큰따옴표, 줄바꿈이 있으면 필드를 큰따옴표로 감쌉니다.
- 필드 안의 큰따옴표는 `""`처럼 두 번 써서 표현합니다.

예를 들어 아래 데이터는 두 레코드, 두 열입니다.

```csv
name,note
"Kim, A.","첫째 줄
둘째 줄과 ""인용문"""
```

줄 수를 단순히 물리적인 줄바꿈 개수로 세면 이 구조를 잘못 판단합니다. 점검 도구는 큰따옴표 안의 줄바꿈을 같은 필드로 처리하고, 닫히지 않은 큰따옴표가 있으면 경고합니다.

## 5. Excel에서는 미리보기에서 세 항목을 확인합니다

Windows용 Excel의 메뉴 이름은 버전에 따라 조금 다를 수 있지만, Microsoft가 안내하는 기본 흐름은 다음과 같습니다.

1. 빈 통합 문서를 엽니다.
2. **데이터 → 데이터 가져오기 → 파일에서 → 텍스트/CSV에서**를 선택합니다.
3. 원본 파일을 고릅니다.
4. 미리보기에서 **파일 원본 또는 인코딩**, **구분자**, **열 배치**를 확인합니다.
5. 날짜·우편번호·상품 코드처럼 자동 변환되면 곤란한 열은 텍스트 형식으로 다룰지 검토합니다.
6. 예상한 행과 열이 보일 때만 불러옵니다.

Power Query 안내에 따르면 텍스트/CSV 가져오기는 구분자와 열 이름·형식을 자동 감지할 수 있습니다. 자동 감지는 출발점일 뿐입니다. 헤더, 첫 데이터 행, 값 안에 구분자가 있는 행을 함께 확인해야 합니다.

## 6. 출처를 모르는 CSV는 수식 시작 문자도 확인합니다

CSV는 텍스트 파일이지만 스프레드시트가 셀 값을 수식으로 해석할 수 있습니다. OWASP의 CSV Injection 테스트 지침은 신뢰하지 않는 입력이 `=`, `+`, `-`, `@` 등으로 시작할 때 스프레드시트에서 수식으로 처리될 수 있다고 설명합니다.

따라서 외부에서 받은 파일이라면 다음을 지키세요.

- 출처와 목적을 확인하기 전에는 경고를 무시하지 않습니다.
- 예상하지 않은 수식 모양의 셀이 있는지 텍스트 미리보기로 봅니다.
- 민감한 파일은 온라인 변환 사이트에 먼저 업로드하지 않습니다.
- 조직의 보안 정책과 최신 스프레드시트 업데이트를 따릅니다.

이 사이트의 점검 도구는 파일을 서버나 외부 API로 보내지 않고 현재 브라우저에서만 앞 20개 레코드를 표시합니다. 파일을 고치는 기능이나 악성 여부를 판정하는 기능은 없습니다.

## 저장 전 최종 체크리스트

- [ ] 원본 복사본을 보존했습니다.
- [ ] BOM 유무와 깨진 문자 `�` 표시를 확인했습니다.
- [ ] 헤더와 데이터 행이 같은 구분자로 나뉩니다.
- [ ] 값 안의 콤마·줄바꿈·큰따옴표가 올바르게 감싸졌습니다.
- [ ] 앞자리 0, 긴 숫자, 날짜가 자동 변환되지 않았습니다.
- [ ] 출처가 불명확한 파일의 수식 시작 문자를 확인했습니다.
- [ ] 미리보기의 행·열 구조가 예상과 맞은 뒤에만 불러오거나 저장합니다.

### 이 글의 확인 범위

2026년 9월 20일에 UTF-8 BOM, 콤마 구분자, 따옴표로 감싼 값이 포함된 작은 샘플을 사이트의 CSV 점검 도구에서 다시 확인했습니다. Excel 메뉴와 동작에 관한 설명은 같은 날 Microsoft 공식 문서와 대조했습니다. Excel의 모든 버전·운영체제 조합을 직접 시험한 결과는 아닙니다.
